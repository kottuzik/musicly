# MILESTONES — מערכת לניהול בית ספר למוזיקה

> מסמך ביצוע עבור Claude Code. מקורות מחייבים: `PRD.md`, `ARCHITECTURE.md`, `DESIGN.md`, `wireframes.png`, `style-guide.png`, `mockups.png` ותיקיית `assets/` הקיימת בפרויקט. במקרה של אי־התאמה, דרישות המוצר וההרשאות ב־PRD קודמות לתמונה; החלטות מימוש ב־ARCHITECTURE קודמות להנחות טכניות; DESIGN מגדיר את המראה, בלי להוסיף פיצ'רים.

## כללי ביצוע — Development Execution Rules

1. **יש לפתח את ה־Milestones לפי הסדר המוגדר להלן.** בכל Milestone יש לממש Vertical Slice עובד, לרבות UI, לוגיקה, Database, הרשאות ובדיקות רלוונטיות — ולא להסתפק במסך סטטי.
2. **בסיום כל Milestone יש לעצור**, להציג למשתמש את היכולות שהושלמו, כיצד לבדוק אותן, תוצאות הבדיקות מול כל סעיפי ה־Definition of Done, מגבלות ידועות וקישור לסביבת בדיקה אם קיים.
3. **אין להתחיל את ה־Milestone הבא ללא אישור מפורש של המשתמש.** אין לפרש שתיקה או הצלחת בדיקות כאישור.
4. עד Milestone הפריסה עובדים **רק מול Supabase Development בענן** ו־Vercel Preview/הרצה מקומית המחוברים אליו. כל שינוי Schema נכתב כ־Database Migration גרסתי ב־Git, מורץ ונבדק ב־Development; אין לשנות את Production במהלך Milestones אלה.
5. **Production:** רק לאחר אישור מפורש של המשתמש, GitHub Actions Workflow מוגן מריץ Migrations על Supabase Production. רק לאחר הצלחתם מתבצע Merge ל־`main` ו־Vercel מפרסמת אוטומטית את הקוד. אין לחשוף סודות Production ל־Claude Code או ל־`.env.local`; אין להשתמש ב־Docker או ב־Supabase Local כתנאי לעבודה.
6. לכל שינוי יש לאמת גם הרשאות בשרת וב־RLS, תרחישי שגיאה, RTL, Responsive ונגישות רלוונטית. אין להוסיף יכולות שאינן ב־PRD.
7. **נכסי עיצוב קיימים:** יש להשתמש בקבצים האמיתיים מתוך `assets/` ולשמור על שמותיהם ונתיביהם בפועל. לפי צילום התיקייה קיימים: `logo-music.webp`, `hero-image.png`, `guitar-m.webp`, `guitar-w.webp`, `piano-m.webp`, `piano-w.webp`, `vocal-m.webp`, `vocal-w.webp`, `both-m.webp`, `both-w.webp`. יש לבדוק בפועל את קיומם, את ייעודם ואת רישיונות השימוש לפני שילובם. להשתמש בלוגו ובתמונות בהקשרים מתאימים לעיצוב המאושר, לא לשייך תמונת אדם למורה/תלמיד אמיתי ללא נתון מתאים, ולא להוסיף גלריה או פיצ'ר תמונות שאינם באפיון. אם קובץ חסר, לדווח ולא להמציא קובץ חלופי.
8. אין ליישם את מסך **ניהול חדרים / מיקומים** שמופיע בהדמיות: הוא מחוץ ל־MVP לפי ה־PRD. את המסכים המאושרים יש להתאים למנהל/מורה ול־Desktop, Tablet ו־Mobile, בלי ליצור מוצר נפרד לכל מכשיר.

## Milestone 1 — בסיס מוצר, סביבות, התחברות והרשאות ✅

**מטרה:** להקים מוצר שניתן להריץ ולבדוק, עם זהות משתמש והרשאות אמיתיות.

**מה יש לממש:**
- Git Repository פרטי ב־GitHub, פרויקט Next.js + React + TypeScript לפי `ARCHITECTURE.md`, חיבור Vercel ל־GitHub, בדיקות בסיסיות, ניהול Environment Variables, RTL ועיצוב בסיסי לפי `DESIGN.md`.
- **בהדרכה צעד אחר צעד למשתמש:** יצירת **שני פרויקטי Supabase נפרדים בענן** — Development ו־Production; שמירת כתובות ו־Publishable Keys בנפרד; חיבור `.env.local` ו־Vercel Preview ל־Development בלבד; הגדרת משתני Production רק ב־Vercel Production, בלי לחבר אליו עדיין פעילות אמיתית. יש להסביר למשתמש בשפה פשוטה את מגבלות התוכניות והשהיית פרויקט Free לא פעיל.
- הקמת Supabase Auth, פרופילים, תפקידי `super_admin`/`admin`/`teacher`, RLS והרשאות התחלתיות; יצירת Super Admin ראשון באופן מבוקר בסביבת Development.
- מסך התחברות, „שכחתי סיסמה”, איפוס באמצעות אימייל, יציאה, מסך בסיסי לפי תפקיד; מניעת אינדוקס. התחלה של ניווט עקבי ב־RTL, שימוש ב־`assets/logo-music.webp` ובנכסים מתאימים נוספים בהתאם לעיצוב.
- Database Migrations גרסתיים, בדיקות הרשאות ובדיקות Build/Typecheck/Lint; אין להקים Storage Bucket עבור תמונות סטטיות הנמצאות ב־`assets/`.

**תוצר מצופה:** ניתן להיכנס כמשתמש מורשה ליישום רספונסיבי; כל תפקיד מגיע לאזור המותר לו, ומשתמש לא מורשה אינו נחשף לנתונים.

**Definition of Done:**
- [ ] שני פרויקטי Supabase בענן נוצרו בהדרכת המשתמש; רק Development מחובר להרצה ולבדיקות, ואין סודות Production מקומיים.
- [ ] כל ה־Migrations של השלב שמורים ב־Git, הורצו בהצלחה ונבדקו על Development בלבד.
- [ ] התחברות, יציאה, איפוס סיסמה, ניווט לפי תפקיד, חסימת גישה לא מורשית ו־RLS נבדקו בפועל.
- [ ] היישום נבנה ללא שגיאות, מוצג בעברית RTL ועובד בתצוגות Mobile/Tablet/Desktop; נכסי `assets/` הנחוצים נטענים בהצלחה.

## Milestone 2 — ניהול מנהלים, מורים ותחומי לימוד ✅

**מטרה:** לאפשר הקמה ותחזוקה של צוות ההוראה ומבנה ההרשאות של בית הספר.

**מה יש לממש:**
- Super Admin מוסיף/מסיר מנהלים, משנה הרשאות, מעביר את תפקיד Super Admin ומונע מצב ללא Super Admin.
- Admin/Super Admin מוסיפים ומנהלים מורים, משייכים כמה תחומי הוראה לכל מורה, שולחים קישור הרשמה למורה; הרשמה עצמית דרך הקישור מעניקה Teacher בלבד, ללא בחירת תפקיד.
- ניהול תחומי לימוד, צבעים ומשך שיעור ברירת מחדל; בשלב זה שינוי משך נשמר כהגדרה, ובהמשך יחובר לטיפול בשיעורים קיימים.
- מסכי רשימת מורים, פרטי מורה, ניהול משתמשים, פרופיל והגדרות רלוונטיות; הרשאות לפי תפקיד, מסננים וחיפוש כפי שהוגדרו.

**תוצר מצופה:** מנהל יכול להקים צוות, תחומי לימוד והרשאות; מורה מוזמן יכול להירשם ולהתחבר לחשבון הנכון.

**Definition of Done:**
- [ ] הוספה/עדכון של מורים ותחומי הוראה עובדים; מורה יכול ללמד כמה תחומים.
- [ ] הזמנת מורה והרשמתו עובדות ללא אפשרות להעניק לעצמו הרשאת מנהל.
- [ ] רק Super Admin יכול לנהל מנהלים; לא ניתן להסיר את Super Admin האחרון.
- [ ] כל שינוי Schema נבדק באמצעות Migration על Development; בדיקות RLS והרשאות עוברות.

## Milestone 3 — תלמידים ושיוך מקצועי למורים ✅

**מטרה:** לנהל תיק תלמיד ומסלול לימוד נפרד לכל תחום, עם הפרדת מידע אישי ומקצועי.

**מה יש לממש:**
- רשימת תלמידים, חיפוש, סינון, יצירה, עריכה ופרטי תלמיד; פרטי קשר, קטינים ופרטי הורה לפי ה־PRD.
- רישום תלמיד לכמה תחומי לימוד; לכל תלמיד–תחום מורה קבוע אחד, רמה ורקע מקצועי נפרדים.
- מנהלים עורכים מידע אישי ומקצועי; מורה רואה רק תלמידים משויכים אליו ועורך מידע מקצועי רק בתחום שהוא מלמד עבורם.
- מצבי פעיל/לא פעיל ותאריך חזרה משוער עם בחירה מחייבת בין התראה להפעלה אוטומטית; השפעת השבתה על שיבוצים תחובר כאשר יפותח מנגנון השיעורים.

**תוצר מצופה:** תיקי תלמידים אמיתיים, עם שיוך מקצועי והרשאות עריכה תקינות.

**Definition of Done:**
- [ ] תלמיד יכול ללמוד בכמה תחומים, עם מורה קבוע ומידע מקצועי נפרדים לכל תחום.
- [ ] מורה אינו יכול לקרוא או לשנות פרטי קשר אסורים, ואינו יכול לערוך תחום שאינו מלמד לאותו תלמיד.
- [ ] הגדרת תאריך חזרה מחייבת בחירה בין התראה להפעלה אוטומטית ללא ברירת מחדל.
- [ ] ה־Migration הוחל ונבדק על Development; תרחישי הרשאה וחיפוש עברו בדיקה.

## Milestone 4 — שעות פעילות, זמינות מורים וימי סגירה

**מטרה:** לבנות מקור אמין למועדים שבהם מותר להציע שיעורים.

**מה יש לממש:**
- שעות פעילות לפי יום, ללא שעות ברירת מחדל; ממשק מנהל להגדרתן.
- מורה מוסיף זמינות בתוך שעות הפעילות באופן מיידי; כל הסרת זמינות, קבועה או חד־פעמית, וכל היעדרות חד־פעמית מחייבות אישור מנהל, גם כשאין שיעורים.
- תור בקשות אישור משותף למנהלים, מניעת טיפול כפול באמצעות בדיקת סטטוס/גרסה ועדכון בזמן אמת.
- חגים ישראליים כהצעות לבחירת מנהל, ימי סגירה מיוחדים ותצוגת זמינות/סגירה. טיפול אוטומטי בשיעורים מושפעים ייבדק לאחר בניית מנגנון השיבוץ.

**תוצר מצופה:** זמינות מורים ושעות בית הספר מנוהלות בממשק, והסרת זמינות דורשת החלטה מתועדת של מנהל.

**Definition of Done:**
- [ ] ניתן להגדיר שעות פעילות שונות לכל יום ולמנוע הוספת זמינות רגילה מחוץ להן.
- [ ] הוספת זמינות מתעדכנת מיידית; הסרה והיעדרות אינן נכנסות לתוקף ללא אישור.
- [ ] שני מנהלים אינם יכולים לאשר/לדחות אותה בקשה בסתירה; השינוי מוצג ללא רענון.
- [ ] חגים וימי סגירה מוגדרים ונשמרים; Migrations והרשאות נבדקו ב־Development.

## Milestone 5 — לוח שנה ושיבוץ שיעורים מקצה לקצה

**מטרה:** לאפשר ניהול שיעור בודד וסדרה שבועית עם מניעת התנגשויות אמינה.

**מה יש לממש:**
- לוח שנה יום/שבוע/חודש, תצוגת שיעור, יצירת שיעור חד־פעמי או סדרה, בחירת תלמיד–תחום–מורה מוסמך, משך ברירת מחדל ודריסה לשיעור חד־פעמי.
- סדרה עם תאריך סיום אופציונלי, כמה מפגשים שבועיים לאותו תלמיד, יצירת מופעים בחלון מתגלגל לפי `ARCHITECTURE.md`.
- בדיקות זמינות והתנגשויות של מורה ותלמיד ב־Database, לרבות שיבוצים מקבילים; שיבוץ חריג מחוץ לשעות פעילות באזהרה למנהל, ושיבוץ מחוץ לזמינות מורה דרך בקשת אישור מורה.
- בקשה חריגה אינה שומרת שעה; אישור בודק התנגשויות מחדש, וסגירת בקשות בסטטוס מתאים כאשר המועד נתפס או עבר.
- Dashboard מנהל ומורה עם שיעורים קרובים, ושינויי לוח בזמן אמת.

**תוצר מצופה:** מנהל יוצר שיעורים אמיתיים ומורה רואה אותם בלוח האישי; המערכת אינה מאפשרת חפיפות מאושרות.

**Definition of Done:**
- [ ] שיעור בודד וסדרה ללא/עם תאריך סיום נוצרים ומוצגים בלוחות הנכונים.
- [ ] התנגשות תלמיד/מורה נחסמת גם בשתי פעולות מקבילות; שיעורים צמודים ללא חפיפה מותרים.
- [ ] בקשה חריגה אינה תופסת שעה; אישור מאוחר מבצע בדיקה חוזרת, וסטטוסים `פג תוקף`/`לא ניתן לשבץ` מתועדים כנדרש.
- [ ] Dashboard ולוח שנה מתעדכנים ללא רענון; Migrations, RLS ובדיקות Responsive עברו ב־Development.

## Milestone 6 — שינויים, ביטולים, שחזורים וסדרות

**מטרה:** להשלים את מחזור החיים של שיעור וסדרה, כולל מקרי קצה והשפעות רוחב.

**מה יש לממש:**
- שינוי שיעור בודד, כל השיעורים העתידיים מתאריך מסוים או כל הסדרה (שיעורי עבר אינם משתנים); טיפול חלקי בהתנגשויות תוך השארת שיעורים בעייתיים במועד המקורי וסימונם לטיפול.
- הפסקת סדרה מתאריך נבחר, ביטול תאריך סיום, חידוש סדרה שכבר הסתיימה מתאריך חדש, ושיבוץ מחדש בכפוף לזמינות.
- ביטול שיעור, סימון „בוטל”, פינוי שעה ומסנן להצגת שיעורים מבוטלים; שחזור בידי מנהלים או מורה המשויך לשיעור, כולל בדיקת התנגשויות.
- שחזור מחוץ לזמינות: מורה שמשחזר בעצמו נחשב למסכים; מנהל זקוק לאישור המורה. שחזור בידי מורה מחוץ לשעות פעילות מחייב אזהרה, בדיקת התנגשויות והתראה למנהלים, ללא אישור נוסף.
- בקשות מורה לשינוי/ביטול, החלטת מנהל, העברה למורה מחליף מוסמך, טיפול בהיעדרויות, שינוי שעות פעילות, שינוי משך תחום וימי סגירה, לרבות רשימות שיעורים מושפעים והחלטות פרטניות.
- הפיכת תלמיד ללא פעיל מבטלת את כל שיבוציו העתידיים ומפנה שעות; מורה לא פעיל לא מקבל שיבוצים חדשים ושיעוריו העתידיים מסומנים לטיפול עם התראת מנהל.

**תוצר מצופה:** מנהל ומורה מבצעים את השינויים המותרים, עם עקביות לוח שנה, היסטוריה והתמודדות עם התנגשויות.

**Definition of Done:**
- [ ] שינוי סדרה אינו משנה שיעורי עבר, ושינויים חלקיים אינם דורסים שיעורים מתנגשים.
- [ ] ביטול מפנה שעה; השיעור נשמר ומתאפשר סינון מבוטלים; שחזור מבצע בדיקת זמינות והתנגשויות.
- [ ] כל מסלולי האישור והחריגות לשינוי/שחזור נאכפים בצד השרת; החלטות מתועדות.
- [ ] שינוי שעות פעילות, ימי סגירה, משך תחום והשבתת תלמיד/מורה מטופלים בהתאם ל־PRD, כולל „דורשים טיפול”.
- [ ] Migrations ובדיקות תרחישי קצה הורצו בהצלחה על Development.

## Milestone 7 — נוכחות, Audit והיסטוריית פעילות

**מטרה:** להבטיח תיעוד אמין של שיעורים ופעולות, ללא פגיעה בהיסטוריה בעת תיקון בדיעבד.

**מה יש לממש:**
- דיווח נוכחות „התקיים”, „התלמיד לא הגיע”, „המורה לא הגיע”, עם הערה אופציונלית; מורה על שיעוריו, מנהל על כל שיעור.
- דיווח ותיקון בכל עת, כולל לפני תחילת שיעור; Audit עם זהות מבצע, מועד וערך קודם/חדש, וצפייה מנהלית.
- ביטול בדיעבד של שיעור שסומן „התקיים” לאחר אזהרה ואישור מנהל; הנוכחות הקודמת נשמרת ב־Audit אך השיעור אינו נספר כשיעור שהתקיים.
- היסטוריית שיעורים ותצוגות מידע מקצועי/נוכחות בהתאם להרשאות; סיכומי Dashboard מדויקים.

**תוצר מצופה:** ניתן לתעד ולתקן נוכחות, לעקוב אחרי השינויים ולסמוך על סיכומי שיעורים.

**Definition of Done:**
- [ ] מורה ומנהל יכולים לדווח ולתקן נוכחות רק לפי הרשאותיהם.
- [ ] כל שינוי סטטוס נוכחות נשמר ב־Audit; מנהל יכול לצפות בהיסטוריה.
- [ ] ביטול בדיעבד דורש אישור, משמר Audit ומעדכן ספירה בצורה נכונה.
- [ ] Migrations, בדיקות הרשאות ותרחישי עבר הושלמו על Development.

## Milestone 8 — התראות, תזכורות, אימייל ותהליכים מתוזמנים

**מטרה:** להשלים תקשורת פנימית אמינה ותזכורות לפי העדפות המשתמשים.

**מה יש לממש:**
- מרכז התראות עם סימון כנקרא והעברה לארכיון ללא מחיקה; בחירה אישית של ערוץ פנימי בלבד או פנימי + אימייל לכל מנהל ומורה.
- תזכורות מורה כבויות כברירת מחדל; בחירת 24/12/2/1 שעות או זמן מותאם, כמה מועדים לכל שיעור, העדפה כללית ודריסה לשיעור מסוים.
- Email Outbox ו־Resend לפי הארכיטקטורה; Supabase Cron למשימות תזכורות, תפוגת בקשות חריגות, הארכת סדרות, חזרה אוטומטית של תלמידים לפי בחירה וטיפול במשימות נדרשות.
- טיפול בכפילויות, שגיאות ושליחה חוזרת; הפרדה מוחלטת בין נמעני בדיקה לנמעני Production.

**תוצר מצופה:** התראות ועדכונים מתקבלים בזמן, העדפות נשמרות ותזכורות נשלחות רק למי שבחר בכך.

**Definition of Done:**
- [ ] ניתן לסמן התראות כנקראו ולהעבירן לארכיון; לא קיימת מחיקה לצמיתות דרך ממשק זה.
- [ ] תזכורות כבויות כברירת מחדל, וכמה מועדים ודריסה לשיעור בודד פועלים.
- [ ] הודעות פנימיות ואימיילים לנמעני בדיקה פועלים בהתאם להעדפות; אין שליחה כפולה בניסיון חוזר.
- [ ] משימות Cron ותפוגות נבדקו מול Development בלבד; סודות מוגנים ו־Migrations הוחלו על Development.

## Milestone 9 — מחיקה רכה, שחזור, מחיקה סופית והרשאות רגישות

**מטרה:** לממש מחזור חיים מלא של נתוני תלמידים ומורים בלי לחשוף מידע מעבר למותר.

**מה יש לממש:**
- Soft Delete ל־30 יום לתלמיד ולמורה, שחזור בתוך התקופה עם בחירת סטטוס פעיל/לא פעיל; מחיקה אוטומטית סופית לאחר 30 יום.
- לאחר מחיקה סופית: מחיקת פרופיל ופרטי קשר; שמירת היסטוריית שיעורים מינימלית בלבד — שם תלמיד, תאריך ושעה, תחום, שם מורה וסטטוס נוכחות, ללא טלפון/אימייל/מידע מקצועי.
- מחיקת היסטוריה לצמיתות לפי אדם, עם חלון אזהרה ואישור; תלמיד — Super Admin או Admin שקיבל הרשאה מפורשת; מורה — כל Admin/Super Admin. שמירה על נתונים משותפים הנחוצים לאחרים בלי להשאיר זהות שנמחקה.
- מורה לא פעיל יכול להתחבר לצפייה בהיסטוריית שיעוריו בלבד; בהפעלה מחדש המנהל בוחר לשחזר זמינות קודמת או לבקש זמינות חדשה.

**תוצר מצופה:** ניתן להשבית, למחוק, לשחזר ולטהר מידע בהתאם למדיניות המוצר ולהרשאות.

**Definition of Done:**
- [ ] שחזור אפשרי בתוך 30 יום בלבד; מחיקה סופית מתוזמנת נבדקה על נתוני בדיקה.
- [ ] אחרי טיהור לא נותרו פרטי קשר/מידע מקצועי של הנמחק בהיסטוריה, בהתראות, בייצוא או ב־Audit בניגוד למדיניות.
- [ ] מחיקת היסטוריה דורשת אזהרה והרשאה מתאימה; ניסיון של משתמש לא מורשה נחסם גם ב־API/RLS.
- [ ] הרשאות מורה לא פעיל ושחזור זמינות נבדקו; Migrations הופעלו ב־Development.

## Milestone 10 — דוחות, ייצוא ועוזר AI לקריאה בלבד

**מטרה:** לספק למנהלים תמונת מצב וכלי איתור מידע, ללא שינוי נתונים אוטונומי.

**מה יש לממש:**
- דוחות וסיכומים, חיפוש/סינון וייצוא CSV/Excel בהתאם לתחומי הנתונים ולהרשאות שב־PRD.
- AI Assistant למנהלים בלבד, המאפשר שאילתות על נתוני בית הספר והצעות למועדים/אפשרויות; אינו יוצר, משנה או מוחק נתונים.
- הגבלת גישה למידע לפי הרשאות, טיפול בשגיאות שירות AI ובמגבלות שימוש; תצוגות UI לפי DESIGN.

**תוצר מצופה:** מנהלים יכולים להפיק מידע, לייצא נתונים מורשים ולהיעזר ב־AI לצורך בירור והצעות.

**Definition of Done:**
- [ ] נתוני דוחות וייצוא תואמים את הנתונים בפועל ואינם כוללים שיעורים מבוטלים בספירת שיעורים שהתקיימו.
- [ ] הרשאות מיושמות גם על Export ועל תשובות AI; מורה אינו נחשף ל־AI מנהלי.
- [ ] ה־AI אינו מבצע פעולת כתיבה; תרחישי כשל API מטופלים בלי לפגוע בנתונים.
- [ ] כל שינוי Schema נבדק באמצעות Migration ב־Development; בדיקות תפקידים ונתונים עוברות.

## Milestone 11 — השלמת ממשק, בדיקות מערכת ופריסה ל־Production

**מטרה:** להביא את כל היכולות שאושרו למערכת עקבית, מאובטחת וניתנת לשימוש בבית הספר.

**מה יש לממש:**
- השלמת מסכים מאושרים לפי DESIGN ו־Mockups, התאמה רספונסיבית ל־Desktop/Tablet/Mobile, RTL, ניווט לפי תפקיד, נגישות ובדיקות בדפדפנים שנקבעו.
- בדיקות End-to-End לתהליכי מנהל/מורה, כולל פעולות מקבילות, שינויי סדרות, בקשות, שחזורים, מחיקות, התראות ו־AI; בדיקות הרשאות, RLS, ביצועים ו־Build.
- סקירת השימוש בתיקיית `assets/` והתאמה חזותית ל־Style Guide; הימנעות מתמונות שאינן חלק מהנכסים או מהדרישות.
- הכנת Supabase Production (Auth, Redirect URLs, SMTP, Secrets, Realtime/Cron והגדרות שאינן מועברות ב־Migrations) ו־Vercel Production; תהליך Deployment המבוקר להלן.

**תוצר מצופה:** אפליקציית MVP פעילה ב־Production עם מסלולי עבודה מלאים, ובסיס להמשך תחזוקה דרך GitHub.

**Definition of Done:**
- [ ] המשתמש אישר במפורש פרסום ל־Production לאחר הדגמה ובדיקות מלאות ב־Development/Preview.
- [ ] GitHub Actions Workflow מוגן הריץ בהצלחה את כל ה־Database Migrations המאושרים על Supabase Production **לפני** Merge ל־`main`; כשל ב־Migration חוסם את הפריסה.
- [ ] לאחר הצלחת ה־Migrations, Merge ל־`main` מפעיל Vercel Production Deployment אוטומטי; Production משתמש רק בפרויקט Supabase Production, וסודות Production אינם נשמרים מקומית.
- [ ] הגדרות Auth, Email, Cron, Realtime, Domains ו־Secrets נבדקו בנפרד ב־Production; לא נשלחות הודעות בדיקה למשתמשים אמיתיים.
- [ ] תהליכי הליבה נבדקו ב־Production בבדיקות מבוקרות; RTL, Responsive, הרשאות, נגישות ושימוש בנכסי `assets/` אומתו.
- [ ] הוצגו למשתמש תוצאות הבדיקות מול ה־Definition of Done; הפיתוח נעצר עד לאישור מפורש להמשך כלשהו.
